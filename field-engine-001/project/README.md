# FIELD ENGINE 001

**Procedural OBAS Spatial Instrument · Version 0.1.0**

A browser instrument built from one continuous material field. Repeated blue lines rise from a light, connected surface into a circulating folded ridge. Pressure gathers and deforms the material. Rupture separates its lobes and releases small, related fragments.

All geometry, motion, marks, and surface patterns are generated by code. No model files, textures, images, external fonts, audio files, or CDN imports are used. Three.js is the only runtime dependency. The application is a static Vite + TypeScript build with optional local Web Audio analysis.

## Quick start

Use Node.js **22.18 or newer** and npm. Node 24 is also supported. Extract the project, open a terminal in its directory, then:

```bash
npm ci
npm run dev
```

Open the address printed by Vite, normally `http://localhost:5173`. The field starts immediately. If your system requests reduced motion, it starts paused; choose **Resume** to animate.

```bash
npm test        # deterministic field and geometry checks
npm run check   # strict TypeScript check
npm run build   # type check + optimized static build in dist/
npm run preview
```

Open the preview address printed in the terminal to inspect the production build. Do not double-click `index.html`: ES modules need an HTTP server.

For a phone on the same network, open the network address printed by `npm run dev`. Touch and synthetic pulse work over ordinary HTTP. Microphone input needs a secure context, typically the deployed HTTPS site; localhost is also supported. See [MDN's microphone requirements](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia).

## Playing the field

| Control | Behavior |
| --- | --- |
| Drag or hold on the field | Compresses the contact area, raises its surrounding rim, and gathers nearby material. |
| Multiple touches | Up to five independent pressure points. Pen pressure controls force on compatible devices. |
| CALM | Slow circulation and gentle folds. |
| PRESSURE | Faster folding, stronger contact response, slight separation. |
| RUPTURE | Five coordinated seams open; fragments rise and travel along the same field. |
| Motion intensity | Changes autonomous speed, folding, and separation. At zero, autonomous time stops; direct pressure and enabled audio can still deform the material. |
| Field density | Changes visible line frequency and fragment count without reallocating the surface. |
| Audio reactive | Enables the selected input. Synthetic pulse is a **silent, 72 BPM visual modulation source**. Microphone measures local signal energy. |
| Pause | Freezes simulation time, motion, and pressure evolution. Resume continues from that state. |
| Reset | Restores CALM, 55% intensity, 58% density, initial phase and fragment seed; clears pressure and disables audio. Honors reduced-motion preferences. |

On mobile, mode buttons stay visible and **Parameters** opens the sliders and audio controls. The panel scrolls on shorter screens. Keyboard controls: **1 / 2 / 3** change modes; **Space** pauses. Focus the field, use **arrow keys** to position pressure, and hold **Enter** to apply it. Native buttons, sliders, the switch, and the source selector are keyboard accessible.

Audio is not recorded, uploaded, or played through the speakers. Switching audio off, resetting, or leaving the page releases microphone tracks. Hiding the page also stops microphone capture; enable it again on return. Permission denials and missing devices produce a message while the field remains usable. Changing sources or switching off during a permission request cancels that request's use; any late-arriving stream is stopped.

## Architecture and file tree

The renderer owns the viewport. Geometry owns topology and allocated buffers. Behavior samples the material. Interaction produces pressure points. Audio produces a normalized envelope. Modes supply continuously interpolated behavior parameters. The UI sends commands and consumes state and telemetry. `FieldEngine` connects those systems and owns their lifecycle.

| Module | Responsibility and useful edit points |
| --- | --- |
| `scene.ts` | Renderer, orthographic composition, resize handling, pixel-ratio limits. |
| `geometry.ts` | Nonuniform surface grid, rest-coordinate cache, dynamic buffers, seeded instanced fragments. |
| `materials.ts` | Palette, antialiased material lines, cross-lines, depth shading, pressure color. |
| `behavior.ts` | Pure field sampler, circulating ridge, folds, seams, local pressure kernels, synthetic pulse. |
| `interaction.ts` | Pointer capture, actual surface ray picking, event coalescing, keyboard pressure, contact decay. |
| `audio.ts` | Microphone permission, AudioContext lifecycle, RMS envelope, silent synthetic input. |
| `modes.ts` | CALM / PRESSURE / RUPTURE parameter profiles and time-based easing. |
| `types.ts` | Shared state and input contracts, defaults, pressure limit, damping helper. |
| `FieldEngine.ts` | Frame scheduling, commands, reset, reduced motion, context recovery, cleanup, telemetry. |
| `ui/controls.ts` | DOM events, control states, input feedback, live readouts. |

The central form and its surroundings share a surface, material, and time source. The field remains legible when a mode changes. Fragments sample the same function rather than becoming an unrelated particle effect.

## Build plan, implemented in this first pass

1. **Foundation:** initialize a minimal Vite/TypeScript app; define shared state, defaults, and the cool paper / ultramarine / vermilion palette.
2. **Continuous material:** generate a grid with higher resolution near its center; displace it into a folded ridge; draw lines on the material with a derivative-antialiased shader.
3. **Behavior:** introduce coordinated circulation, local folding, pressure kernels, sector separation, and seeded fragments. Keep rest coordinates immutable so repeated updates do not accumulate drift.
4. **Input:** pick the deformed surface, add smoothed pointer/pen/touch pressure and keyboard access, then add optional microphone or synthetic modulation.
5. **Instrument controls:** mode selection, intensity, density, audio on/off and source, pause, reset, and responsive controls.
6. **Delivery:** verify deterministic behavior and mesh validity, compile the production build, include static deployment automation, and document extension boundaries.

## How the primitives become behavior

| Primitive | Implementation |
| --- | --- |
| POINT | Contacts and seeded fragments occupy the same material coordinates. |
| LINE | Repeated material-space lines bend with the surface. |
| FIELD | A continuous height surface extends beyond the core and fades into its background color. |
| EDGE | Changes in slope and material line density make folds visible. |
| PRESSURE | Bounded Gaussian kernels compress contact centers and lift their rims. |
| REPETITION | Related ridges, bands, and fragments share phase and spatial rules. |
| OCCLUSION | An opaque, depth-tested surface hides material behind its folds. |
| RUPTURE | Coordinated angular seams separate the ridge and lift fragments. Topology remains connected in V1. |
| DENSITY | A continuous shader frequency and bounded instance count change visible concentration. |
| VELOCITY | A time-based phase controls circulation; eased mode and input states avoid discontinuities. |

V1 is an analytic procedural field, not a fluid solver or learned system. Its behavior is deterministic for a fixed sequence of inputs and frame timing. Mode interpolation itself is independent of frame rate. The mobile and desktop tiers use different tessellation and fragment budgets, so their renderings are not pixel-identical.

## Performance and lifecycle

- **12,769 surface vertices / up to 220 fragments** on coarse-pointer devices or initial viewport widths below 760px; **25,921 vertices / up to 360 fragments** otherwise.
- One surface mesh and one instanced fragment mesh. No postprocessing, shadows, physics package, texture downloads, or per-fragment draw calls.
- Static radial coordinates are cached; typed buffers and work objects are reused. Pressure kernels omit negligible tails beyond three radii.
- Pointer movement is coalesced to one ray pick per pointer per simulation frame.
- Pixel ratio starts capped at 1.5 on mobile and 1.8 on desktop. Sustained low measured frame rates reduce it toward 1. This reduces GPU load; it does not solve CPU-bound overload.
- Delta time is capped at 50 ms to prevent large jumps after interruptions. Very slow devices therefore advance simulation more slowly than wall time.
- Hidden pages stop frame scheduling. Reduced-motion preferences start the scene paused. WebGL context loss shows a recoverable message; restored contexts resume rendering.
- The FPS display measures the animation loop; it is not a hardware benchmark. A pause retains rendering for responsive resizing and controls while skipping simulation work.

## Deployment

### GitHub Pages

The supplied workflow builds and publishes the contents of `dist/`.

1. Create a GitHub repository and add this project, including `package-lock.json` and `.github/workflows/deploy.yml`. Keep dependencies and build output out of Git.
2. Use a `main` branch, or adjust the workflow's branch filter.
3. In **Settings → Pages → Build and deployment**, select **GitHub Actions**.
4. Push to `main`, or run the workflow manually from **Actions**.
5. Open the deployed URL reported by the Pages job after it completes.

`vite.config.ts` uses `base: './'`, so bundled asset URLs are relative and work at both an origin root and a repository subpath. The app has one route and needs no SPA rewrites. See the [Vite deployment guide](https://vite.dev/guide/static-deploy.html) and [GitHub Pages custom workflows](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

For an empty repository, the usual commands after configuring a remote are:

```bash
git init -b main
git add .
git commit -m "Build FIELD ENGINE 001"
git remote add origin https://github.com/YOUR-ACCOUNT/YOUR-REPOSITORY.git
git push -u origin main
```

### Other static hosts

Use `npm ci` to install, `npm run build` to build, and **dist** as the publish directory. No environment variables, backend, database, or runtime server are required. HTTPS enables microphone access. Upload the contents of `dist/` together, preserving its `assets/` directory.

## Validation and current limits

The included Node tests check finite values under extreme inputs, local pressure effects, frame-rate-independent mode easing, reproducible seeds, pulse bounds, valid mesh indices, and deterministic geometry reset. `npm run build` also performs strict TypeScript checking.

The initial delivery has not been visually inspected in a real browser or on a physical phone. GPU shader rendering, touch ergonomics, browser permission flows, and sustained frame rate still need device testing. The numerical checks do not establish those results. Use a current browser with [WebGL 2 support](https://threejs.org/docs/pages/WebGLRenderer.html).

Suggested first device pass: try all three modes; drag across the ridge and background; use two touches; drag both sliders to their extremes; test microphone allow/deny/off and tab switching; pause and reset; rotate the phone and open Parameters. Check that the field remains usable after each action.

Current limits: fixed camera; connected height-surface topology; RMS microphone energy rather than pitch or beat detection; silent synthetic modulation; no audio synthesis, data import, session recording, or persistence. These are specific V1 boundaries, with the next steps below.

## Three extension paths

### A. LiDAR / depth-data input

Add a `DepthSource` adapter that returns a normalized height grid and confidence mask from a depth image or downsampled scan points. Use that grid as the rest field, then apply OBAS motion and pressure as displacement on top. Preserve a blend control between measured depth and procedural motion so the original spatial structure stays legible.

Begin with local depth-image input and a bounded grid; it keeps runtime-generated geometry and avoids importing a rendered 3D model. Normalize units and orientation, handle holes explicitly, and perform conversion in a worker if necessary. Full room scans with overhangs will need a point-cloud or voxel representation because V1's height field cannot represent multiple heights at the same x/z coordinate. Surface normals, color, and roughness can later drive spatial sound.

### B. Archive-data-driven field

Add an `ArchiveSource` that maps records to stable, seeded attractors. Date can position records; relationships can shape connecting lines; record density can condense the field. Preserve each record's persistent ID and distinguish explicit metadata from inferred connections.

Start with a small JSON export of actual archive records. Let a selected record reveal its title and provenance while its neighborhood changes field pressure. Save the mapping rules and seed with each study so an interpretation can be reproduced. This gives Archive Engine / MZTV a spatial way to navigate real relationships without treating arbitrary motion as evidence.

### C. Sound-performance instrument

Separate `AudioInput` from a new `SoundEngine`. Map pressure position to stereo location, contact velocity to excitation, and local field structure to pitch or timbre. Use a small polyphonic Web Audio graph with smooth envelopes, a master gain, and bounded voice count.

Begin with four voices and explicit sound-on activation. Keep mappings spatial: each voice should belong to a region or behavior rather than driving a global visual pulse. Add performance presets, timestamped gesture capture, and optional MIDI clock/control only after the core sound is playable. Microphone monitoring should remain off unless explicitly enabled.

Each path can keep `FieldEngine`, the mode controller, and the control surface while replacing or extending one input contract. Preserve this V1 as the reference implementation and branch each study independently.
